# Arc SQL Power BI report

The original `arc_insights_dashboard_jumpstart_V2 (1).pbit` template is retained
as the upstream baseline. `ArcSqlEstate/` is its source-controlled extraction,
created with pbi-tools 1.2.0 using TMDL model serialization.

Three focused pages are generated by `tools/build-layout.mjs`, using the
existing report pages as visual templates so the 1280 x 780 canvas, dark theme,
Segoe UI typography, navigation, slicers, cards, spacing, and colour treatment
remain consistent:

- `Security Patching CVE Audit` - Update Manager assessment coverage, missing
  patches by machine and classification, a complete missing-patch detail table,
  and a separate machine/KB/CVE exposure table. Missing patches come from
  Resource Graph; CVEs are mapped dynamically from Microsoft Security Response
  Center CVRF documents and are never inferred from patch names.
- `Best Practices` - a normalized Arc SQL assessment aligned to the PDF report
  contract, including check ID, check name, category, status, severity,
  affected asset, current and expected values, evidence source, and
  remediation. Tier 1 checks use Arc inventory; unavailable Tier 2
  `SqlAssessment_CL` evidence is shown explicitly as `Not Assessed`.
- `DMV Audit` - a deliberately data-gated page documenting the collection,
  evidence-store, audit-domain, and planned-visual contract. It does not show
  fabricated DMV findings before a customer-owned data source is configured.

Migration assessment detail is intentionally not repeated on these pages. It
remains in the existing `ESU Forecast` report page.

The ESU forecast keeps SQL Server Developer edition workloads visible for
planning, but assigns zero OS and SQL ESU cost to those rows because their
development/test entitlement is expected to be provided through Visual Studio
subscriptions.

## Resource Graph datasets added

- `view_arg_scope_validation` - Arc machine and Arc SQL visibility by
  subscription and resource type.
- `view_migrate_projects` - Azure Migrate project discovery.
- `view_patch_assessment_summary` - Update Manager assessment coverage and
  missing patch counts by classification.
- `view_missing_patches` - individual missing Windows and Linux patches.
- `dim_patch_cve_mapping` - authoritative MSRC-only KB-to-CVE mappings.
- `dim_linux_patch_cve_mapping` - normalized Linux vendor advisory mappings;
  providers import Canonical Ubuntu Security Notices and Red Hat CSAF data for
  supported releases, retaining only exact package/version keys present in the
  current estate.
- `view_patch_cve_mappings` - calculated machine-level CVE exposure derived
  from `view_missing_patches`, MSRC, and Linux vendor mappings without another
  Resource Graph query.
- `view_best_practice_findings` - calculated instance/database findings derived
  from the existing keyed Arc SQL inventory tables.

Power BI prompts once for anonymous access to `api.msrc.microsoft.com`,
`ubuntu.com`, `access.redhat.com`, and the Microsoft Learn SQL build-reference
page when the template is first opened.
Azure Resource Graph authentication remains organizational-account based.

Linux CVE exposure uses strict vendor matching. Ubuntu rows are emitted only
when the machine release, binary package name, and Update Manager target
package version exactly match a Canonical USN package record. Candidate
packages without a published matching advisory remain visible as missing
patches but are not assigned speculative CVEs.

Red Hat Enterprise Linux rows use the public Red Hat Security Data API's CSAF
package index. RHEL major release, binary RPM name, and target epoch-version-
release must match a released RHSA package exactly. Matching normalizes only
an implicit zero epoch and an optional architecture suffix; it does not use
lexicographic RPM version comparisons or reuse RHSA mappings for downstream
distributions such as AlmaLinux, Rocky Linux, or Oracle Linux.

The template already contained dedicated Resource Graph queries for Arc
machines, Arc SQL instances, Arc SQL databases, extensions, and resource tags.
The added evidence reuses those imports and resolves resource filters through
the existing `fact_keys` and `fact_resources` spine.

## DMV data recommendation

Use a customer-owned Fabric Lakehouse as the preferred durable store:

1. Run the approved read-only DMV and runtime validation scripts through Arc
   Run Command.
2. Write structured JSON output to ADLS Gen2 or OneLake using an immutable
   `assessment_run_id`, collection timestamp, tenant, subscription, machine,
   instance, and database identifiers.
3. Ingest the files into Lakehouse Delta tables with a Fabric pipeline or
   notebook.
4. Build a small star schema with assessment run, machine, SQL instance,
   database, feature finding, and runtime validation entities.
5. Connect Power BI through Direct Lake when Fabric is available, or Import mode
   with incremental refresh for smaller estates.

This pattern preserves history, supports trend analysis, keeps customer data in
the customer's tenant, and separates Resource Graph refresh cadence from
privileged DMV collection.

For customers without Fabric, use an ADLS Gen2 account with partitioned Parquet
files and a Power BI dataflow as the lightweight alternative. Log Analytics is
suited to operational telemetry and short-retention exploration, but is less
appropriate as the canonical store for structured assessment evidence.
